# Decisions

Choices made during the build, and why.

| # | Decision | Why |
|---|---|---|
| 1 | **Vercel hosts the dashboard instead of Render.** | The intake supplied a Vercel token, not a Render key. |
| 2 | **Dashboard is FastAPI with server-rendered HTML, not Streamlit.** | Streamlit needs a long-running server with websockets, which Vercel's short-lived functions do not provide. FastAPI pages run as one Vercel function. It also allowed a deliberately simple UI: plain pages, big buttons, plain-English labels, almost no JavaScript. |
| 3 | **Scheduler is Vercel Cron** (`vercel.json`: `30 0 * * 1,4` run, `30 0 * * 5` weekly summary). | The app already runs on Vercel, and keeping the schedule there avoids storing database and email secrets in GitHub. Vercel Cron calls `/api/cron/run`, which is protected by `CRON_SECRET`. On the Hobby plan Vercel starts the job somewhere in the scheduled hour (05:30-06:29 IST). `.github/workflows/run_plan.yml` holds the same cron as a backup that runs only when the repository variable `USE_GITHUB_SCHEDULER` is `true`, so the plan never runs twice. |
| 4 | **Database is Neon Postgres**, created through the Neon API (project `freshroots-demand-planning`, region ap-southeast-1, pooled connection). | The intake supplied a Neon API key. The same SQLAlchemy code runs on SQLite for tests and local work. Serverless connections use `NullPool`; Neon's pooler reuses connections. |
| 5 | **Emails go through Resend from `onboarding@resend.dev`.** All three recipient roles currently point at the Resend account owner's address. | No `EMAIL_FROM` or recipient addresses were supplied, and the Resend account has no verified domain. Resend's test sender only delivers to the account owner, so that is the only address that can receive mail today. A test send succeeded. Changing `EMAIL_TO_*` and `EMAIL_FROM` in Vercel settings is all that is needed later. |
| 6 | **Dashboard logins were generated** (raghav, procurement, deepa); only PBKDF2 hashes are stored. Passwords were delivered once by email and the body was not stored. | `DASHBOARD_USERS` was blank. |
| 7 | **Explanations use templates.** | No Anthropic key was supplied. The Claude path (model `claude-haiku-5-5`, number validation, cache) is built and tested with a stub client, and switches on when `ANTHROPIC_API_KEY` is set. |
| 8 | **The public repo contains the 5 sample CSVs.** | The brief calls them sample data. Real SAP exports should come through `DATA_SOURCE_URL`, not the repo. |
| 9 | Order quantities are rounded **up** to whole units. | Never under-order because of rounding. |
| 10 | Stock in several locations is **summed per SKU**; the **oldest** As_Of_Date decides staleness. | The real data will have more than one warehouse. |
| 11 | If the SAP export is behind (no row for the last complete week), the run uses the newest week available and shows a warning. Gaps inside a SKU's history raise MISSING_WEEKS. | A late export should be visible, not silently treated as zero sales. |
| 12 | **Reasons: optional for approvals and small changes, required for material changes.** A change that moves the quantity by more than `review.material_change_pct_of_standard` (25%) of the SKU's standard order needs a reason; anything smaller is logged as "Quantity changed (no reason given)", approvals as "Approved as recommended". | Reconciles two instructions: reasons optional (review of 23 Oct) and "require a reason for material quantity overrides" (improvement brief). The SKU007 case (pause to 3 units, standard 400) stays optional. |
| 13 | Approving is not allowed on an exception (there is nothing to approve); the reviewer enters a quantity instead. | Exceptions never get an automatic recommendation. |
| 14 | Decisions are **soft-deleted** (marked removed, kept in the log). | Keeps the audit trail. |
| 15 | Reruns on the same date create run #2, #3... and never overwrite. | Idempotency requirement. |
| 16 | `windows.demand_baseline` (default `long` = avg12) was added to the rules file. | Needed for the backtest sensitivity table (avg4 vs avg12). The production rule is unchanged. |
| 17 | `docs/judgment_log.md` is regenerated on each local run. On Vercel the filesystem is read-only, so the same file is served live at `/judgment-log.md`. | Requirement to document overrides over time. |
| 18 | Retries: 3 attempts with 2 s then 4 s backoff for connectors, database writes and email. Validation errors are not retried (they will not fix themselves). | Requirement, kept short enough for a 60 s serverless limit. |
| 20 | **No login on the dashboard** (changed on request after the first deployment). Pages open directly; every change form asks for the person's name, which is stored with the decision and remembered in that browser. `AUTH_REQUIRED=true` turns the login page back on; the generated logins still work. | Requested by the project owner for simpler access. Trade-off: anyone with the link can view the plan and record decisions, and names are not verified. Cron endpoints stay protected by `CRON_SECRET`. |
| 21 | **Zoho Inventory** (not Zoho Books) holds the purchase orders. | The demo organization was created in Zoho Inventory; it has the same purchase-order API. |
| 22 | Stock on order = purchase orders with status issued/open/partially received that are not fully received, counting only the units not yet received. Drafts, received, closed and cancelled orders are ignored. Cover = (on hand + on order) / weekly demand. `open_orders.include_in_cover` in the rules file switches this off. | Prevents re-ordering stock already in transit. Rule 1 (high demand) is unchanged and still fires when sales are rising, even with stock on order. |
| 23 | If Zoho cannot be reached after 3 attempts, the plan **still runs** without stock on order and shows a warning on the dashboard and in the email. | A Zoho outage should not leave Raghav without a plan; the warning makes the gap visible. |
| 24 | The Zoho login is a Self Client refresh token with read and create access (create was needed once, to load the demo data). | Simplest Zoho OAuth flow for a server job. A read-only token is enough for production. |
| 25 | **The landing page is Raghav's action list**: SKUs grouped as Reorder now, Demand rising, Pause the next order and Needs your judgment, each with the triggering rule in plain words, the suggested quantity, and Approve / Change / Undo in place. OK SKUs are folded into a "fine, no order needed" section (with "Order anyway"). A "How the flags are decided" card shows the live thresholds. | He opens the dashboard to make decisions, not to read counts. |
| 26 | **Charts live only on the Analytics tab** (changed after review: an earlier version put a small bar on every front-page SKU and a chart on the SKU page, which made the decision page busier). Two charts: weeks of stock for every SKU against its own target range, and weekly units sold for one chosen SKU with its 4- and 12-week averages. Both have a table view; the sales chart has hover values. Each run stores the 16 weeks of sales it saw (schema v3). | The decision page stays a plain to-do list; the analysis is one click away. |
| 27 | **Night theme** across the dashboard, with a faint decorative chart pattern in the background (no data, hidden from screen readers). Chart colours are the reference palette's dark-mode steps, validated against the dark card surface. Emails stay light, since mail clients render them that way. | Requested for a demand-dashboard look and stronger colour contrast. |
| 28 | The front page states progress in words: decisions made so far (with the date and time) for the plan of a given date, and how many are left, due before the next scheduled plan (Mon/Thu 06:00 IST). | Makes the deadline explicit: once the next plan runs, today's suggestions are replaced. |
| 29 | **Every SKU needs Raghav's decision, including "no order needed" ones.** OK SKUs have their own section on Today and an Approve: no order button plus Change in place on Today and Recommendations; they count toward the decisions left. Approve all covers them too (never exceptions). (Changed after review: OK SKUs used to have no button.) | Raghav signs off the whole plan, not just the flagged part. |
| 30 | **No Exceptions or Runs tabs.** Exceptions already appear on Today under "Needs your judgment" (the old address forwards there). Run history stays at /runs for the IT team (linked from the failure email and from the failed-run notice on Today) but is not in the menu. | Keeps Raghav's menu to what he uses: Today, Recommendations, Decisions, Analytics, Settings. |
| 31 | **One current decision per SKU per plan; every decision is an event.** A repeated click stores nothing new. A different decision replaces the current one (kept, marked *replaced*, with the value it replaced in `previous_qty`). Undo applies only to the current decision and returns the SKU to waiting; the event stays, marked *undone*. Counts on every page come from `Store.decision_progress`. On upgrade, older duplicate rows (three identical SKU003 approvals two seconds apart on plan #2) were marked *replaced*, not deleted. | Root cause of the duplicate SKU003 rows and differing counts: every click inserted a row, and the Decisions page mixed all plans while Today counted only the current one. |
| 32 | **Stock on order counts only if it arrives before stock on hand runs out** (`open_orders.count_only_if_arrives_before_stockout`). Orders arriving later, or with no delivery date, are listed with the reason and not counted. Run-out date = run date + (on hand ÷ weekly demand) weeks. | Blindly subtracting every open PO can hide a stockout that happens before the PO lands. Undated orders are not counted because their arrival cannot be checked; this errs towards reordering. |
| 33 | **The documented quantity rules are unchanged** (standard, or 1.5x when demand is rising, even with stock on order). Each suggestion now carries a check of where stock ends up after the order (below the minimum / inside the range / above the maximum) as a warning. | The case defines the quantities; changing them silently would alter the business rules. The check makes cases like SKU001 (1,000 on order + 750 suggested = 9.86 weeks, inside 6-14) verifiable. |
| 34 | **Plan status on Today** (safe / check warnings / not reliable) is derived only from what the run recorded (`runs.data_info`: source, read time, sales weeks, stock dates, SKU counts, purchase orders) and today's date. Stock older than the stale limit, a late sales export or many SKUs with bad data make the plan "not reliable". The bundled CSVs are labelled demo data. | Raghav must know whether a plan is safe to act on; nothing is invented. |
| 35 | Within each group on Today, SKUs are ordered by urgency: least weeks of stock first (most excess first for Pause). Supplier lead time is not in the data, so "runs out before replenishment" uses on-order arrival dates only. | Uses the evidence that exists. |
| 36 | Today, Analytics and the rule summaries use the rules version the plan was made with, not the latest saved version. | Historical plans stay interpretable after rules change. |
| 37 | **Excel import is all or nothing.** Every row is checked (SKU in this plan, Approve/Change, whole-number quantity, duplicate SKUs, material-change reason, file made for this plan) before any is applied; rows matching decisions already recorded are skipped and reported. | Avoids partial or duplicate application. |
| 38 | **No Recommendations tab.** It showed the same SKUs and buttons as Today in a table. Its filters (distributor, category, status, only waiting) moved to a row on Today; Approve all on a filtered view approves only the SKUs shown; older plans open on Today with `?run=` (linked from the Decisions history and run history). `/recommendations` forwards to Today with the same filters. | One page for deciding; nothing lost. Filters matter at 400 SKUs. |
| 19 | No ML forecasting. | Sixteen weeks of history cannot support it. Listed as a future option. |
